# Treetop Management — Practice Management App

## What This Is
A full-stack practice management system for a CPA firm. Handles contacts, projects (formerly
"engagements"), time tracking, billing, invoicing, AR, staff management, notes, reports,
due dates, and automations. Deployed as a Node/Express + SQLite server on one LAN machine
with Electron desktop clients connecting over the network. Not a SaaS product.

---

## How to Run

```bash
# Terminal 1 — API server (port 3001)
cd server
npm run dev          # nodemon auto-restart (sets NODE_ENV=development)
# or: npm start      # plain node

# Terminal 2 — React frontend (port 5173)
cd client
npm run dev

# Reset database to clean seed data (demo users + sample data)
cd server
npm run seed

# Empty database (production-like; bootstrap flow required to log in)
cd server
npm run seed:empty
```

Client proxies all `/api` requests to `localhost:3001` via Vite config.

### Electron dev

```bash
cd client
npm run electron:dev        # starts Vite + Electron together (recommended)
npm run electron:start      # Electron only (expects Vite already running)
npm run electron:build-test # builds Vite bundle then opens in Electron (no NSIS)
```

### Building the installer

```bash
cd client
npm run dist    # local build only — produces release/ folder, does NOT publish
npm run release # builds + publishes to GitHub Releases (requires GH_TOKEN env var)
```

## Database Schema (key tables)

```sql
users           id, username (unique), password (bcrypt), full_name, email,
                role (admin/manager/staff), default_hourly_rate, active

engagements     id, client_name, engagement_type, tax_year, due_date, status,
                assigned_staff, priority, budgeted_hours, budgeted_amount, recurrence_frequency

projects        id, engagement_id (FK), client_name, project_type, entity_type, period_label,
                status, current_due, original_due, priority, extended, completed_date,
                primary_partner, manager, preparer, reviewer, in_charge

contacts        id, name, type (individual/business), email, phone, client_type, ...

time_entries    id, engagement_id, project_id, staff_member (TEXT), user_id (FK→users),
                date, hours, billing_rate, notes, billable, service_code,
                pay_period_id, entry_status (draft/submitted/released)

pay_periods     id, period_number, year, start_date, end_date,
                status (Open/Released/Locked)
pay_period_user_status  pay_period_id, user_id, status, released_at  (per-user release tracking)

staff_rates     id, staff_member, hourly_rate, effective_date
service_codes   id, code, description, number, category, default_rate, billable_default, active

invite_keys     id, key_hash (SHA-256), username, full_name, email, role,
                status (pending/redeemed/revoked), created_by (FK→users),
                created_at, redeemed_at, redeemed_user_id

app_meta        key, value  (KV store — holds bootstrap_token_hash, bootstrap_used)
```

Migration pattern: `server/db/migrate.js` uses `PRAGMA table_info` guards before each
`ALTER TABLE`. New columns on existing tables go here, not in schema.js.

## Auth Architecture

- **JWT** stored in `localStorage` as `treetop_auth_token`, 24h expiry
- **Secret resolution** (in `server/middleware/auth.js`):
  1. `process.env.JWT_SECRET` — always wins if present (normal path)
  2. `NODE_ENV === 'test'` — auth skipped entirely; placeholder secret
  3. `NODE_ENV === 'development'` — insecure dev-only fallback + console warning
  4. Otherwise (production without secret) → `process.exit(1)`, server refuses to start
- **Middleware:** `requireAuth` in `server/middleware/auth.js` — all routes after
  `app.use(requireAuth)` in `app.js` require a valid JWT
- **Flow:** POST /api/auth/login → `{ token, user }` → stored → Bearer header on every request
- **401 handling:** `client/src/api/client.js` removes token + redirects to `/login` on any 401
- **AuthContext:** `useAuth()` → `{ user, loading, login, logout, isAdmin, isManager }`

### Bootstrap / invite-key flow

1. Fresh server → `checkBootstrap()` in `index.js` → generates token → saves hash to
   `app_meta.bootstrap_token_hash` → raw token printed to console + saved to `BOOTSTRAP_TOKEN.txt`
2. First admin hits `/bootstrap` with token → server verifies hash, creates admin account,
   calls `consumeBootstrapToken()` (sets `bootstrap_used = true`, clears token file)
3. Admin generates invite keys via Settings → `POST /api/invite-keys` (admin only) →
   returns raw key once, stores only the SHA-256 hash
4. New user hits `/register` with invite key → `POST /api/auth/redeem` → verifies hash,
   checks status (pending only), creates account, marks key redeemed

## Server URL / LAN Config (Phase 1)

The server binds to `0.0.0.0:3001` so it's reachable from any LAN machine.

Clients store the server address in `localStorage` as `treetop_server_url`. All API calls
read it via `getServerUrl()` from `client/src/config/serverConfig.js`. On first launch
(or if no URL is stored) the app shows `ServerSetup.jsx` which calls `testConnection(url)`
against `GET /api/health` (unauthenticated) before saving.

The `GET /api/health` endpoint in `app.js` is registered before `requireAuth` so it's
always reachable without a token.

## Electron Architecture (Phases 3–6)

### File locations
- `client/electron/main.cjs` — main process (must be .cjs because package.json has `"type":"module"`)
- `client/electron/preload.cjs` — context bridge, runs before renderer
- `client/electron/electron-dev.cjs` — dev launcher script
- `client/package.json` `"build"` section — electron-builder config (NSIS, productName, publish)

### Dev vs production load
- **Dev:** `ELECTRON_START_URL` set → `mainWindow.loadURL(devServerUrl + hashRoute)`
- **Production:** `ELECTRON_START_URL` not set → `mainWindow.loadFile(dist/index.html, { hash })`
- HashRouter is used (not BrowserHistory) so `file://` protocol works without a server

### Multi-window (Phase 4b)
- `moduleWindows` Map in main.cjs: one BrowserWindow per module key (max)
- `openModuleWindow(key)` opens `/m/<key>` route, which renders inside `StandaloneLayout`
- IPC channels (renderer → main via `window.__treetop__`):
  - `open-module` — validated against MODULE_LABELS whitelist
  - `open-external` — validated `^https?:\/\/` before `shell.openExternal`
  - `logout-all` — closes all module windows, sends `force-logout` to main window
- IPC channels (main → renderer): `force-logout`

### Preload bridge (`window.__treetop__`)
Exposed via `contextBridge.exposeInMainWorld`. Raw `ipcRenderer` and `shell` are never
exposed. The surface:
```js
window.__treetop__ = {
  isElectron: true,
  platform,           // 'win32' | 'darwin' | 'linux'
  appVersion,         // from package.json
  openModule(key),    // sends 'open-module' IPC
  openExternal(url),  // sends 'open-external' IPC (main validates https?://)
  logoutAll(),        // sends 'logout-all' IPC
  onForceLogout(cb),  // subscribes to 'force-logout'; returns cleanup fn
}
```

### Critical security/compat settings (do not change without understanding why)
- `contextIsolation: true` — renderer cannot access Node APIs directly
- `nodeIntegration: false` — no Node in renderer
- `sandbox: false` — **required**: Electron 20+ sandbox prevents preload scripts from
  loading when their path resolves inside an ASAR. contextIsolation + no nodeIntegration
  still provides the security boundary, but sandbox must be false for ASAR-packed apps.

### Preload path resolution
The preload is in `asarUnpack` so it lands at `resources/app.asar.unpacked/electron/preload.cjs`.
`PRELOAD_PATH` in main.cjs uses `fs.existsSync` (not `app.isPackaged`) because
`app.isPackaged` reads false when running from `win-unpacked/` even though an ASAR is present:
```js
const unpackedPath = path.join(process.resourcesPath, 'app.asar.unpacked', 'electron', 'preload.cjs')
if (fs.existsSync(unpackedPath)) return unpackedPath   // packaged
return path.join(__dirname, 'preload.cjs')             // dev / build-test
```

### Installer
- electron-builder NSIS, `perMachine: false` (user install, no admin required)
- `productName: "Treetop Management"`, `executableName: "Treetop Management"`
- Installer output: `client/release/Treetop Management Setup x.x.x.exe`
- Unsigned — SmartScreen will warn on first run, users click "More info → Run anyway"

## Time Tracking Architecture

Pay periods are biweekly, 26/year. Period 10 (May 11–24, 2026) is the "current" period in seed data.

`TimeTracking.jsx` holds all state and passes down to children:
- `EntryForm` — log new entries, staff auto-fills from auth user (cannot be changed by staff)
- `DailyGrid` — shows entries for selected date
- `TimesheetView` — full period grid by staff/date
- `TimeFilterSidebar` — calendar widget + filters
- `BottomTabs` — 4 tabs: MTD Hours / Period Summary / Time Release / Alerts

`timeSummaryApi` endpoints:
- `GET /api/time-summary/mtd?staff=` — month-to-date with by-category breakdown
- `GET /api/time-summary/period/:id` — full period grid
- `GET /api/time-summary/alerts` — missing days, low hours, overbudget
- `GET /api/time-summary/daily-hours?staff=&from=&to=` — dense map including 0-hour days

Entry status flow: `draft` → (user releases) → `submitted` → (admin/manager releases) → `released`

Per-user release status tracked in `pay_period_user_status` (separate from the period-level status).

## Key Patterns to Follow

1. **API routes** — every new route goes in `server/routes/`, registered in `server/app.js`
   below the `app.use(requireAuth)` line (unless public like `/api/auth` or `/api/health`)
2. **Admin-only routes** — add a local `requireAdmin` guard at the top of each handler:
   ```js
   if (req.user.role !== 'admin') return res.status(403).json({ error: 'Admin access required' })
   ```
3. **New tables** — `CREATE TABLE IF NOT EXISTS` → `server/db/schema.js`;
   new columns on existing tables → `server/db/migrate.js` with `PRAGMA table_info` guard
4. **Client API** — add a file in `client/src/api/` that imports `{ api }` from `./client`
   and exports a named object like `fooApi`
5. **Don't use `useCallback` for simple loaders** unless they're a dependency of a `useEffect`
6. **Toast notifications** — `import { useToast } from '../context/ToastContext'`
   → `toast.success('msg')` or `toast.error('msg')`
7. **No breaking other sections** — all existing routes and pages must remain functional;
   only add/extend, never remove existing behavior
8. **Module windows** — new navigable modules need an entry in `client/src/config/modules.js`
   AND a matching key in `MODULE_LABELS` in `client/electron/main.cjs`
9. **Hashing tokens** — always use `hashToken()` from `server/utils/crypto.js`;
   never store raw tokens in the DB
10. **Electron IPC** — new IPC channels need a handler in `main.cjs` AND a wrapper on
    the contextBridge in `preload.cjs`; never expose raw `ipcRenderer`
